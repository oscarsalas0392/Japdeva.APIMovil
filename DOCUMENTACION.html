Japdeva API Móvil — Guía de arquitectura y configuración

1. Arquitectura general

La solución utiliza una arquitectura de microservicios con un API Gateway centralizado. Cada microservicio es independiente, tiene su propia base de datos PostgreSQL y se comunica con el servicio de colas vía gRPC.

3. Flujo de una solicitud

Solicitud pública (sin sesión)

App  →  Gateway  POST /Usuarios/api/Autenticar
          ↳ LimitarSolicitudesMiddleware   (rate limit)
          ↳ ValidarTokenMiddleware         (ruta pública → sin validación)
          ↳ CrearTokenMiddleware           (genera JWT interno para Usuarios)
          ↳ EnviarTraceIdMiddleware        (inyecta X-Trace-Id)
          ↳ Ocelot enruta a :7075

Usuarios  →  valida JWT interno
          →  autentica credenciales
          →  responde RespuestaModel<T>

Gateway   →  GestionarTokenRespuestaMiddleware (ajusta token en respuesta)
          →  App recibe la respuesta

Solicitud autenticada (ej. crear reclamo)

App  →  Gateway  POST /Reclamos/api/Reclamo/AgregarReclamo
          ↳ LimitarSolicitudesMiddleware
          ↳ ValidarTokenMiddleware    (valida JWT del cliente)
          ↳ CrearTokenMiddleware      (genera JWT para Reclamos)
          ↳ Ocelot enruta a :7219

Reclamos  →  valida JWT interno
          →  procesa reclamo
          →  publica mensaje gRPC a Colas (notificación por correo)
          →  responde

Colas     →  almacena mensaje pendiente
EnvioCorreos (background) → consume gRPC → envía correo SMTP

6. Comunicación entre servicios (gRPC)

El servicio Colas expone una API gRPC que el resto de microservicios consume para publicar mensajes asíncronos (notificaciones de correo, etc.).

Métodos disponibles

service ColaService {
  rpc PublicarMensaje(PublicarMensajeRequest)             returns (MensajeResponse);
  rpc ObtenerMensajesPendientes(ObtenerMensajesRequest)   returns (stream MensajeResponse);
  rpc ObtenerMensajePorIdRpc(ObtenerPorIdRpcRequest)      returns (MensajeResponse);
  rpc ActualizarMensajeEnProceso(ActualizarMensajeRequest) returns (ActualizarMensajeResponse);
  rpc ActualizarMensajeExitoso(ActualizarMensajeRequest)   returns (ActualizarMensajeResponse);
  rpc ActualizarMensajeFallido(ActualizarMensajeRequest)   returns (ActualizarMensajeResponse);
}

Seguridad gRPC

El servicio Colas valida cada llamada mediante TokenGrpcInterceptor, que verifica la cabecera GRPC_CLAVE_INTERNA. Esta clave debe ser idéntica en el servidor Colas y en todos los microservicios clientes.

7. Seguridad y autenticación

Cadena de tokens

Cliente  →  Gateway         (valida JWT del cliente)
         ↓
Gateway  →  Microservicio   (genera JWT interno por servicio)
         ↓
Microservicio               (valida JWT interno: ISSUER / AUDIENCE / CLAVE_SECRETA propios)
Regla crítica de coincidencia ISSUER_USUARIOS del Gateway debe ser idéntico al ISSUER de Usuarios.
Lo mismo aplica para AUDIENCE y CLAVE_SECRETA de cada servicio.
Si no coinciden, el microservicio rechazará todas las solicitudes con 401.

Rutas públicas (sin JWT de cliente)

8. Correo electrónico

El servicio EnvioCorreos maneja todo el envío de correos de forma asíncrona mediante colas:

  1. Otro microservicio publica un mensaje a Colas vía gRPC.
  2. EnviarCorreoPorColaBackGroundService (en EnvioCorreos) consume los mensajes pendientes.
  3. SmtpService envía el correo usando MailKit.
  4. El resultado (éxito/fallo) se guarda en la tabla CorreosHistorico.
  5. Si falla, reintenta hasta CORREO_MAX_INTENTOS veces.

Configurar Gmail (App Password)

  1. Habilitar Verificación en dos pasos en la cuenta de Google.
  2. Ir a: Cuenta de Google → Seguridad → Contraseñas de aplicación.
  3. Crear una nueva contraseña para la aplicación (genera 16 caracteres).
  4. Usar esa contraseña en SMTP_CONTRASENA — no la contraseña normal.
  5. Configurar SMTP_HOST=smtp.gmail.com, SMTP_PUERTO=465, SMTP_USAR_SSL=true.

9. Caché y servicios en segundo plano

Los microservicios usan un patrón de caché en memoria que se actualiza periódicamente sin afectar las solicitudes activas:

│  BackGroundService                  │  ← se ejecuta cada ~5 min
│  └─ LlenarCacheXxxAsync(traceId)    │  ← carga datos de BD en memoria
└─────────────┬───────────────────────┘
              │
     ┌────────▼────────┐

              │
     ┌────────▼────────┐

      { "Nombre": "Parametros",   "RecrearBaseDatos": false, "Ejecutar": true },
      { "Nombre": "Reclamos",     "RecrearBaseDatos": false, "Ejecutar": true },

Ejecución

# Desde la raíz de la solución:
dotnet run --project Japdeva.APIMovil.BaseDatos

# La herramienta solicita interactivamente:
#   → Contraseña de PostgreSQL
#   → Confirmación antes de recrear bases de datos

Estructura de scripts SQL

BasesDatos/
└── {NombreBD}/
    ├── BaseDatos/   → CREATE DATABASE
    ├── Tablas/      → CREATE TABLE IF NOT EXISTS
    ├── Indices/     → CREATE INDEX IF NOT EXISTS
    └── Datos/       → INSERT ... WHERE NOT EXISTS  (idempotentes)
Scripts idempotentes Todos los scripts de Datos/ usan el patrón WHERE NOT EXISTS (SELECT 1 FROM "Tabla" WHERE "id" = X) para que ejecutarlos múltiples veces no duplique registros.
SituaciónAcción
Primera instalaciónEjecutar con todas las BDs en "Ejecutar": true
Agregar tabla nuevaAgregar script en Tablas/, ejecutar solo esa BD
Agregar datos semillaAgregar script en Datos/, ejecutar
Recrear BD completaPoner "RecrearBaseDatos": true para esa BD (elimina y recrea todo)

11. Orden de inicio en desarrollo

  1. PostgreSQL — debe estar corriendo y aceptar conexiones en el puerto 5432.
  2. BaseDatos — solo la primera vez o cuando hay cambios de esquema.
  3. Colas — debe estar disponible antes que los demás (los otros servicios conectan a gRPC al iniciar).
  4. Usuarios · Reclamos · Parametros · EnvioCorreos — en cualquier orden entre sí.
  5. Gateway — último; enruta a todos los anteriores.
Visual Studio / VS Code Usar el perfil "Launch All Microservices" en .vscode/launch.json para iniciar múltiples servicios con un solo comando.

12. Agregar un nuevo microservicio

  1. Crear el proyecto 
    dotnet new webapi -n Japdeva.APIMovil.NuevoServicio
dotnet sln add Japdeva.APIMovil.NuevoServicio
  2. Referenciar Common en el .csproj 
    <ProjectReference Include="..\Japdeva.APIMovil.Common\Japdeva.APIMovil.Common.csproj" />
  3. Configurar Program.cs 
    WebApplication.CreateBuilder(args)
    .AgregarPostgreSQL<NuevoServicioDbContext>()
    .AgregarServiciosMicroservicios()
    .AgregarClienteColasGrpc()          // si necesita enviar mensajes a Colas
    .AgregarServiciosNuevoServicio()    // extensión propia del servicio
    .Build()
    .ConfigurarServiciosMicroservicios();
  4. Variables de entorno en launchSettings.json 
    {
  "ISSUER":            "https://localhost:7075",
  "AUDIENCE":          "apiNuevoServicio",
  "CLAVE_SECRETA":     "EstaEsUnaClaveSuperSeguraDe32CharsPrueba12345!!",
  "CONNECTION_STRING": "Host=localhost;Port=5432;Database=NuevoServicio;Username=postgres;Password=1234",
  "COLAS_URL":         "https://localhost:7001",
  "GRPC_CLAVE_INTERNA":"claveInterna123"
}
  5. Registrar en el Gateway — launchSettings.json 
    "RUTAS_CON_TOKEN":             "Usuarios,Parametros,Reclamos,EnvioCorreos,NuevoServicio",
"ISSUER_NUEVOSERVICIO":        "https://localhost:7075",
"AUDIENCE_NUEVOSERVICIO":      "apiNuevoServicio",
"CLAVE_SECRETA_NUEVOSERVICIO": "EstaEsUnaClaveSuperSeguraDe32CharsPrueba12345!!",
"ROL_NUEVOSERVICIO":           "NuevoServicio"
  6. Registrar en el Gateway — appsettings.Development.json (Ocelot) 
    {
  "UpstreamPathTemplate": "/NuevoServicio/{everything}",
  "DownstreamPathTemplate": "/{everything}",
  "DownstreamHostAndPorts": [{ "Host": "localhost", "Port": 7XXX }]
}
  7. Crear la base de datos
    Agregar carpeta BasesDatos/NuevoServicio/ con los scripts SQL. Registrar en appsettings.json de BaseDatos y ejecutar la herramienta.
  8. Decorar todos los controladores con [Authorize] 
    [Authorize]
[ApiController]
[Route("NuevoServicio/api/[controller]")]
public class MiController : ControllerBase { ... }
